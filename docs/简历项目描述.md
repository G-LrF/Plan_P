## 使用说明（先读这一节，最重要）

### 简历描述的三条铁律

**铁律 1：只写你亲手做过的**

面试官不会只看你写了什么，他们会**挑一条深入追问三层**：

```text
简历：「通过 Redis 缓存将查询 QPS 提升 10 倍」
面试官：「为什么用 Cache-Aside 而不是 Write-Through？」
       「缓存穿透你怎么处理的？」
       「缓存和数据库不一致的那个窗口期，用户会看到什么？」
```

**如果你只是照教程敲了一遍、没想过这些问题，第三问就崩了。**
而一旦有一条被问崩，**面试官会怀疑你简历上所有内容**。

**铁律 2：量化数据必须是你测出来的**

```text
❌ 写「性能提升 10 倍」（你没测过）
✅ 写「热点查询 P95 从 45ms 降至 3ms（wrk 压测，100 并发）」（你测过）
```

**如果确实还没测**，就先不写数字，或者写"计划验证"。**编数字是最容易被戳穿的地方**，因为面试官会问"你怎么测的"。

**铁律 3：未完成的明确标注**

```text
❌ 「使用 Kubernetes 完成服务编排」（实际没做，一问就露）
✅ 「规划中：基于 Kubernetes 完成服务编排与自动扩缩容」（诚实且显示你有规划）
```

**标注"规划中"不扣分，反而显得你有清晰的技术路线。编造才会致命。**

后端  Python 3.13 + FastAPI + Pydantic + SQLAlchemy 2.0
数据  MySQL 8.0
工程  Git（Conventional Commits）+ 自动化测试

核心工作：

1. 接口设计与契约管理

   解决 MySQL 空闲连接被服务端断开导致的隔夜首次请求失败问题。
   将数据存储从内存迁移至 MySQL，实现进程重启后数据不丢失。

4. 跨域与多环境适配
   后端 CORS 白名单与前端开发代理双重方案，
   前端统一使用相对路径 /api，避免硬编码后端地址导致的环境切换故障。
   数据库凭据通过环境变量注入，实现本地/测试/生产配置与代码分离。

5. 测试体系
   编写 126 项自动化测试，分四层：
   - 进程内接口测试（38 项）：路由、校验、业务、CORS 响应头
   - 真实 HTTP 冒烟测试（20 项）：端口连通、编码链路、数据持久化

   - 全链路联调测试（18 项）：浏览器 → 代理 → 后端 → 数据库
   测试采用唯一标记造数 + 自动清理，对存量数据免疫，可重复执行。

### 这一版必须准备的面试问题

**关于 Docker**

```text
Q: 多阶段构建解决了什么问题？
A: 构建阶段需要编译器、依赖包，运行阶段只需要解释器和代码。
   不分阶段的话，镜像里会带着几百 MB 的构建工具，既大又有安全风险
   （暴露编译环境、多装不必要的包）。分阶段后最终镜像只保留运行所需。

Q: 为什么用 depends_on 还不够，要加 healthcheck？
A: depends_on 只保证"容器启动"，不保证"服务可用"。
   MySQL 容器启动到能接受连接有几秒到几十秒的窗口，
   应用这时候连过去会失败退出。加 healthcheck 让 compose 等到
   健康才启动依赖方。

Q: 容器里数据会丢吗？
A: 容器删除后其内部文件系统就没了。所以数据库数据必须放在 Volume 里，
   Volume 的生命周期独立于容器，docker compose down 不会删除（除非加 -v）。
```

**关于 Redis**

```text
Q: 缓存和数据库不一致怎么办？
A: 这是缓存方案的固有代价，只能缩短窗口期，不能消除。
   我们的策略是 Cache-Aside：读时先查缓存，未命中查库并回填；
   写时先更新数据库，再删除缓存（不是更新缓存）。
   删缓存而不是更新缓存，是为了避免并发写入导致缓存里留下旧值。
   同时设置过期时间作为兜底。

Q: 为什么删除缓存而不是更新缓存？
A: 更新缓存时，如果两个写请求并发，可能后写的先执行，
   导致缓存里是旧的。删除缓存让下次读重新加载，出问题的概率更低。
   （这是经典的 Cache-Aside 讨论，能答出这层说明真的想过）

Q: 缓存穿透、击穿、雪崩分别是什么？
A: 穿透 —— 查不存在的数据，缓存永远不命中，每次都打到数据库。
      解决：缓存空值 + 布隆过滤器。
   击穿 —— 某个热点 key 过期瞬间，大量请求同时打到数据库。
      解决：互斥锁重建，只让一个请求去查库。
   雪崩 —— 大量 key 同时过期，或 Redis 整体故障。
      解决：过期时间加随机值，做多级缓存兜底。
```

### 2. 这个项目最难的地方是什么

**准备一个真实的、有细节的故事。** 比如：

```text
最难的是数据从内存迁移到数据库这一步。

看起来只是改个存储位置，实际要考虑很多：
- 原代码里 id 是 max(id)+1 算出来的，并发下会撞车主键，
  必须改成数据库 AUTO_INCREMENT
- 时间戳要自动维护，不能靠代码记得写
- 连接池要配 pre-ping，否则 MySQL 空闲 8 小时断开连接，
  池里存着死连接，隔夜第一次请求必崩，而且重启又好了，
  极难排查
- 测试也要改：原来假设"启动时是干净的 2 条数据"，
  换成数据库后数据会累积，必须改成自造数据 + 自清理
```

**为什么这个故事好**：有具体的技术细节、有踩坑、有反思。**面试官能从中看出你是不是真的做过。**

### 3. 如果流量涨 100 倍，你怎么办

**这是运维岗的经典问题。** 分层回答：

```text
1. 先测量，不猜测 —— 看监控哪个环节先顶不住
   （CPU？内存？数据库连接数？响应时间 P95？）
2. 应用层：加实例 + Nginx 负载均衡（无状态才能水平扩展，
   所以 Session 要放 Redis，不能放内存）
3. 数据库层：加索引、读写分离、热点数据进 Redis
4. 异步化：非核心链路丢进消息队列，削峰
5. 最后才考虑分库分表（成本最高，能不做就不做）
```

### 4. 服务挂了你怎么排查

**准备一套有顺序的方法论**：

```text
1. 先看服务活着没：健康检查接口 / 容器状态
2. 看日志：容器日志 → 应用日志 → 错误堆栈
3. 看资源：CPU / 内存 / 磁盘 / 连接数
4. 看依赖：数据库通不通？Redis 通不通？
5. 看监控：挂之前有没有异常指标（延迟上涨、错误率飙升）
```

**"有方法论"比"我知道怎么修"更重要** —— 因为故障千奇百怪，但排查顺序是通用的。

### 5. 为什么不直接用 K8s

```text
✅ 好答案：K8s 解决的是大规模多节点编排的问题。
   我这个项目单机部署，Docker Compose 完全够用，
   上 K8s 会增加复杂度但没有收益 —— 单机 K8s 还要额外承担
   控制面的资源开销。
   但我会在本地用 minikube 学习，理解 Deployment、Service、
   探针、HPA 这些概念，因为它们代表的服务治理思路
   （声明式、自愈、弹性）是有价值的。
```

**能说"什么时候不该用什么技术"，比会用更显水平。**

## 红线提醒：这些绝不能写

| ❌ 不能写 | 为什么 | ✅ 改成 |
|---|---|---|
| 精通 XXX | "精通"是最高级的词，一问细节就露 | 熟悉 / 使用过 / 实践了 |

| 使用 K8s 部署 | 没做就是撒谎 | 规划中：基于 K8s 完成编排 |
| 团队协作开发 | 个人项目 | 独立完成 |
| 微服务架构 | 3 个组件不叫微服务 | 前后端分离 + 多中间件架构 |

**记住一句话**：
> **简历的作用是让你获得面试机会，不是让你在面试中出丑。**
> 写得保守一点，进了面试靠真实能力赢；写得夸张，面试现场会崩得更难看。
